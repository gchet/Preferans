# Переход на libp2p без собственного сервера (ветка experiment-net)`n`nСтатус: игровой транспорт, приглашения PREF2, сервис комнат внутри приложения, настройки подключения и`nнетчек переведены на libp2p; Pion из приложения удалён (остаётся в экспериментальных инструментах`nnetcheck/natlab и netcheck/ipv6). Публичное лобби на ntfy.sh выбирает сервис комнат автоматически (internal/p2p/lobby.go, internal/app/lobby.go).`nНе сделано: голос по libp2p, синхронизация каталога между игроками,`nпроверка внутри APK на разных сетях.

Цель: игроки подключаются друг к другу с минимумом ручных действий, используя только публичные
сервисы (без своего VPS, сигналинг-сервера и TURN).

## Что измерено (стенд netcheck/natlab)

Телефон на LTE Vodafone UA (CGNAT, NAT endpoint-independent) против домашней сети за одним роутером,
ПК и двух VM Hyper-V (двойной NAT: WinNAT + роутер). Приглашение передаётся через ntfy.sh.

- 15 из 15 соединений libp2p перешли на прямой путь (DCUtR): 0,5-16 с после первого соединения
  через публичный relay (типично 5-8 с). До связи в целом около 20 с, почти всё это резервирование
  relay при старте узла (его можно сделать заранее при запуске приложения).
- Приглашение ~315-385 байт (3 relay-адреса). До ограничения было 3,3 КБ при лимите ntfy 4 КБ.
- DHT-поиск комнаты (Provide/FindProviders) занимает около 100 с: для лобби не подходит.
- WebRTC/Pion: телефон-ПК то соединялся, то нет (по умолчанию Pion делает ~8 проверок на пару),
  телефон-VM за двойным NAT не соединялся ни при каких настройках.

Выборка небольшая (один телефон/оператор). Нужны повторы в других сетях (см. «Проверки»).

## Что заменяет что

| Сейчас | Станет |
|---|---|
| internal/network.Peer (Pion, DataChannel preferans-v1) | internal/p2p.Conn (libp2p-поток, длина+JSON; те же Message/Status/Open/Send/Close/DiagnosticRoute) |
| Код PREF1 с SDP + ответный код (2 обмена кодами) | Код PREF2: table, seat, nonce, key, peer ID, 2-3 relay-адреса; один код, без ответа |
| STUN/TURN (SelectICEServers, CheckTURN, turn_check.go) | публичные relay libp2p, AutoNAT, DCUtR; TURN и STUN-настройки уходят |
| internal/rooms + cmd/signaling (каталог комнат, обмен SDP) | короткий код стола -> тема ntfy.sh, где хост публикует приглашение; публичный список столов - необязательная тема ntfy |
| Голос (web/src/voice.ts, браузерный WebRTC) | отдельное решение (см. ниже) |

Pion после замены остаётся нужен только если голос продолжает идти через браузерный WebRTC
(это сам WebView, не Go-зависимость). Go-код Pion (internal/network, netcheck, диагностика) удаляется.

## Прототип в ветке

internal/p2p: Node (libp2p-хост, bootstrap, DHT как источник relay, AutoRelay, AutoNAT v2, NAT-PMP/UPnP,
DCUtR), Invite (компактное приглашение), Dial, Conn. Тест на loopback без публичной сети:
go test ./internal/p2p. Приложение (internal/app) ещё не переведено.

## Решения и риски

1. Relay публичных узлов ограничивает соединение (по умолчанию порядка 2 минут и десятков КБ).
   Игра рассчитана на прямое соединение (DCUtR). Если прямое не получилось, нужно переподключаться
   через те же relay: уже есть механизм восстановления соединения (rememberConnectionLoss).
2. Голос. Варианты: (а) оставить браузерный WebRTC, передавая его SDP по libp2p-потоку (без TURN голос
   будет соединяться реже игры); (б) передавать Opus по libp2p-потоку (WebCodecs AudioEncoder/Decoder
   в WebView2 и Android WebView, работает только при прямом пути из-за лимита relay). Решение нужно принять
   до начала миграции интерфейса.
3. Каталог комнат. Публичный список столов можно вести темой ntfy (cache since=all), но у него нет
   администрирования и защиты от спама. Если список обязателен, это отдельное решение.
4. Android: go-libp2p использует wlynxg/anet для перечисления интерфейсов (в untrusted_app netlink закрыт).
   Тесты natlab шли из adb shell, а не из APK: проверить внутри APK netcheck.
5. Размер: бинарник natlab вырос с ~17 до ~27 МБ (Windows). Нужна проверка влияния на APK.
6. Зависимость от публичных сервисов (bootstrap IPFS, relay, ntfy.sh): они могут исчезнуть или ввести
   ограничения. Запасной путь - ручной обмен кодом PREF2 (relay-адреса остаются валидными только
   пока живёт резервирование).

## Этапы

1. (сделано) Стенд, замеры, прототип internal/p2p.
2. Нода при старте приложения; Invite(seat) -> PREF2; Join(PREF2); удаление Answer из UI; тесты.
