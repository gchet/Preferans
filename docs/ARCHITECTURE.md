# Архитектура

## Компоненты
| Каталог | Роль |
|---|---|
| web/src | Общий HTML/TypeScript/CSS интерфейс |
| internal/game | Правила, состояния и расчёт записей |
| internal/app | RPC, ведущий/участник, боты, сохранения, пауза и восстановление |
| internal/p2p | libp2p: узел, приглашения PREF2, пробитие NAT, потоки игры и запросы к сервису комнат |
| internal/rooms | Каталог комнат, составы, сигналы, администрирование (работает внутри приложения игрока) |
| internal/storage | Локальные настройки и сохранения |
| internal/ai | Необязательные обращения к моделям |
| internal/secrets | Платформенная защита ключей |
| cmd/preferans | Windows оболочка и headless запуск для тестов |
| cmd/signaling | Необязательный отдельный сервер комнат (только для разработки и тестов по HTTP) |
| mobile | API Go для gomobile |
| android/app | Kotlin WebView, микрофон, обновления, Android Keystore |
| config | Встроенные параметры и промпты |
| locales | Общие языковые JSON-ресурсы для Go, WebUI и Android |

## Интерфейс и локальный API
Vite собирает WebUI в web/dist; Go встраивает результат в приложение.
Отдельный Vite-конфиг собирает страницу администрирования в
internal/adminweb/static для сигналинг-сервера.

В Windows Go запускает HTTP-сервер на loopback и открывает WebView2.
В Android Kotlin запускает Go через gomobile и показывает тот же URL
в Android WebView. Общие действия — HTTP POST /api с JSON action и параметрами.
Состояние получается периодическим опросом. Игровой движок исполняется в Go,
а не в браузере.

Случайный токен локального API передаётся через fragment URL и заголовок
X-Preferans-Token. API не предназначен для удалённого доступа.
Отдельный HTTP-сервер Wi-Fi обновлений обслуживает APK и манифест; доступ к нему
и firewall настраиваются отдельно.

Мост PreferansAndroid используется для платформенных функций: разрешений
микрофона, установки APK, сохранения журнала, работы с защищёнными ключами.
В Windows такие функции реализованы Go/нативной оболочкой.

## Комнаты и восстановление

Игроки соединяются по libp2p без своего сервера. Каждое устройство имеет постоянный
ключ (peer ID); публичные bootstrap/relay-узлы IPFS дают первичный доступ в сеть и
резервирование адреса за NAT, дальше узлы переходят на прямое соединение (DCUtR). Код
приглашения PREF2 содержит peer ID, адреса и одноразовый Nonce места; ответный код не нужен. В приглашение
входят адреса локальной сети (чтобы устройства в одной сети соединялись напрямую), публичные адреса и до
трёх relay. Гость сначала пробует прямые адреса (6 с) и только потом идёт через relay; соединения с
участником и relay защищены от обрезки диспетчером соединений; в журнал пишутся события пробития NAT
и закрытия соединений.
Каталог комнат реплицируется между устройствами: каждое устройство хранит у себя копию долговечной части каталога
(названия комнат, надгробия удалений комнат и партий, история партий — RoomSnap в internal/rooms/sync.go; участники и стол не
реплицируются). Последователь раз в период лобби запрашивает у ведущего снимок (op snapshot по тому же libp2p-протоколу)
и вливает его в свой сервис; устройство, ставшее ведущим, перед объявлением забирает снимки у прочих живых ведущих.
Слияние идемпотентно: надгробия побеждают, название — с более поздним Updated, партия — с большей Revision;
одинаковые названия после слияния различаются номером. Удаление комнаты теперь оставляет надгробие.
Тот же код rooms.Server, что в cmd/signaling, исполняется внутри приложения игрока и обслуживает
каталог комнат/партий и сигналы. Игроки ничего не вводят: публичное лобби (общая тема ntfy.sh)
выбирает ведущего сервиса комнат — самую старую установку среди доступных (объявления раз в 60 с,
только peer ID и адреса relay, без публичного IP). Остальные устройства автоматически пользуются
сервисом ведущего; пока игрок в комнате или за столом, ведущий не меняется; при исчезновении ведущего
роль переходит к следующему. Код сервиса PREF2 в настройках скрыт (ручной выбор оставлен в коде).
Полный игровой расклад и сохранения остаются на устройствах. Ведущий создаёт стол и является
авторитетным игровым узлом. Публичные relay libp2p ограничены по времени и объёму, поэтому
игра рассчитана на прямое соединение. Роль ведущего автоматически не передаётся.

Комната вмещает до четырёх устройств. Выбранная комната сохраняется; комната
по умолчанию используется только при отсутствии выбора. Имена не являются
идентификаторами: каждое устройство имеет собственный секрет room-session.
Клон VM должен получить собственный каталог данных.

В комнате доступны голосовой чат и сбор участников. После создания стола
участники переходят на игровое поле. Голос передаётся браузерным WebRTC (только публичные STUN, без TURN); локальный
микрофон и общий динамик можно отключить, звук другого участника можно отключить
отдельно. При игре только с ботами микрофон не показывается.

Оборванное соединение восстанавливается автоматически через сервис комнат (новое приглашение).
Неподтверждённые/устаревшие действия не применяются; партия ждёт участников.
Ручная пауза синхронна для всех и останавливает время партии. Снять её может
установивший игрок. Выход участника не завершает стол ведущего.

Офлайн-режим использует локальную комнату и тот же игровой движок; сервер
и интернет для игры с ботами не требуются.

## Сохранения и данные
Локальные настройки не входят в состояние стола. Договорённости стола сохраняются
с партией и синхронизируются ведущим. Незавершённые сохранения для продолжения
показываются ведущему; история и каталог итогов доступны участникам.
Имена для итогов комнаты объединяются, идентификаторы устройств для соединения —
нет. Сервер хранит метаданные партий, а не полные расклады.
