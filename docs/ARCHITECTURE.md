# Архитектура

## Компоненты
| Каталог | Роль |
|---|---|
| web/src | Общий HTML/TypeScript/CSS интерфейс |
| internal/game | Правила, состояния и расчёт записей |
| internal/app | RPC, ведущий/участник, боты, сохранения, пауза и восстановление |
| internal/p2p | libp2p: узел, приглашения PREF2, пробитие NAT, потоки игры и запросы к сервису комнат |
| internal/rooms | Каталог комнат, составы, сигналы, администрирование (работает внутри приложения игрока) |
| internal/storage | Локальные настройки и сохранения |
| internal/ai | Необязательные обращения к моделям |
| internal/secrets | Платформенная защита ключей |
| cmd/preferans | Windows оболочка и headless запуск для тестов |
| cmd/signaling | Необязательный отдельный сервер комнат (только для разработки и тестов по HTTP) |
| mobile | API Go для gomobile |
| android/app | Kotlin WebView, микрофон, обновления, Android Keystore |
| config | Встроенные параметры и промпты |
| locales | Общие языковые JSON-ресурсы для Go, WebUI и Android |

## Интерфейс и локальный API
Vite собирает WebUI в web/dist; Go встраивает результат в приложение.
Отдельный Vite-конфиг собирает страницу администрирования в
internal/adminweb/static для сигналинг-сервера.

В Windows Go запускает HTTP-сервер на loopback и открывает WebView2.
В Android Kotlin запускает Go через gomobile и показывает тот же URL
в Android WebView. Общие действия — HTTP POST /api с JSON action и параметрами.
Состояние получается периодическим опросом. Игровой движок исполняется в Go,
а не в браузере.

Случайный токен локального API передаётся через fragment URL и заголовок
X-Preferans-Token. API не предназначен для удалённого доступа.
Отдельный HTTP-сервер Wi-Fi обновлений обслуживает APK и манифест; доступ к нему
и firewall настраиваются отдельно.

Мост PreferansAndroid используется для платформенных функций: разрешений
микрофона, установки APK, сохранения журнала, работы с защищёнными ключами.
В Windows такие функции реализованы Go/нативной оболочкой.

## Комнаты и восстановление

Игроки соединяются по libp2p без своего сервера. Каждое устройство имеет постоянный
ключ (peer ID); публичные bootstrap/relay-узлы IPFS дают первичный доступ в сеть и
резервирование адреса за NAT, дальше узлы переходят на прямое соединение (DCUtR). Код
приглашения PREF2 содержит peer ID, адреса и одноразовый Nonce места; ответный код не нужен. В приглашение
входят адреса локальной сети (чтобы устройства в одной сети соединялись напрямую), публичные адреса и до
трёх relay. Гость сначала пробует прямые адреса (6 с) и только потом идёт через relay; соединения с
участником и relay защищены от обрезки диспетчером соединений; в журнал пишутся события пробития NAT
и закрытия соединений.
Каталог комнат реплицируется между устройствами: каждое устройство хранит у себя копию долговечной части каталога
(названия комнат, надгробия удалений комнат и партий, история партий — RoomSnap в internal/rooms/sync.go; участники и стол не
реплицируются). Последователь раз в период лобби запрашивает у ведущего снимок (op snapshot по тому же libp2p-протоколу)
и вливает его в свой сервис; устройство, ставшее ведущим, перед объявлением забирает снимки у прочих живых ведущих.
Слияние идемпотентно: надгробия побеждают, название — с более поздним Updated, партия — с большей Revision;
одинаковые названия после слияния различаются номером: название остаётся у более старой комнаты (по Created), более новая
получает номер. Удаление комнаты оставляет надгробие; закрытие стола тоже (ClosedTable{ID, At}, стол с Opened ≤ At
закрывается и на других репликах, стол, открытый позже закрытия, остаётся), поэтому устаревший стол вчерашней партии не
блокирует комнату на сервисе, где закрытие не выполнялось.
Тот же код rooms.Server, что в cmd/signaling, исполняется внутри приложения игрока и обслуживает
каталог комнат/партий и сигналы. Игроки ничего не вводят: публичное лобби (общая тема ntfy.sh)
выбирает ведущего сервиса комнат: сначала настольные устройства, среди равных — самую старую установку
(телефон засыпает вместе с сервисом, поэтому в объявлении есть признак `m`, и компьютер приоритетнее телефона;
объявления раз в 60 с, только peer ID, адреса relay и до двух адресов локальной сети, без публичного IP; объявляется каждое
живое устройство, а не только ведущий, чтобы все видели одних и тех же кандидатов). Остальные устройства автоматически
пользуются сервисом ведущего; пока игрок за столом, ведущий не меняется; при исчезновении ведущего
роль переходит к следующему. Если лучший по приоритету кандидат недоступен именно этому устройству
(нынешнего ведущего прощаем до двух сбоев подряд), берётся следующий, вплоть до собственного сервиса,
а не остаётся мёртвый сервис. Каталоги обмениваются не только с ведущим, но и (в фоне) с двумя другими
живыми кандидатами, поэтому комната, созданная на «чужом» сервисе при временном расколе, попадает во все каталоги.
Если живой кандидат (свежее объявление) недоступен этому устройству, создание комнат отклоняется (lobbyUnsettled,
«Сервис комнат ещё определяется»), пока он не ответит или его объявление не устареет: на разошедшихся сервисах иначе
появились бы две комнаты с одним названием. Вход в существующие комнаты не блокируется.
Адреса relay ведущего сменились — он объявляется сразу; пока relay нет или ведущий не отвечает,
опрос лобби повторяется каждые 10 с (до двух минут подряд). Код сервиса PREF2 в настройках скрыт (ручной выбор оставлен в коде).
Полный игровой расклад и сохранения остаются на устройствах. Ведущий создаёт стол и является
авторитетным игровым узлом. Публичные relay libp2p ограничены по времени и объёму, поэтому
игра рассчитана на прямое соединение. Роль ведущего автоматически не передаётся.

Комната вмещает до четырёх устройств. Выбранная комната сохраняется; комната
по умолчанию используется только при отсутствии выбора. Имена не являются
идентификаторами: каждое устройство имеет собственный секрет room-session.
Клон VM должен получить собственный каталог данных.

В комнате доступны голосовой чат и сбор участников. После создания стола
участники переходят на игровое поле. Голос передаётся браузерным WebRTC (только публичные STUN, без TURN); локальный
микрофон и общий динамик можно отключить, звук другого участника можно отключить
отдельно. При игре только с ботами микрофон не показывается. Запасной путь: если WebRTC пары не поднялся за 25 с,
звук этого игрока идёт кадрами Opus (WebCodecs, 20 мс, 24 кбит/с, пачки по 60 мс; `web/src/voice-relay.ts`) по игровому каналу
libp2p: гость -> ведущий -> остальные гости (Go: `internal/app/audio.go`, пакет `audio`, действия `audio-send`/`audio-poll`;
очередь короткая, устаревшие кадры отбрасываются, медленный канал не блокирует остальных). Каждая сторона выбирает путь для
каждого собеседника сама: пока WebRTC с ним не `connected`, звук от него принимается по столу, после соединения WebRTC звук по
столу игнорируется. Способ выбирается в настройках («Подключение» → «Голос»): автоматически, только WebRTC, только через стол
(хранится в localStorage устройства). Запасной путь работает, пока создан стол (в комнате до начала партии игрового канала нет);
без WebCodecs Opus он недоступен. Через стол эхоподавление браузера может не учитывать воспроизведение, лучше наушники.
События голоса (состояние WebRTC, типы кандидатов ICE, выбранная
пара, поток аудио, ошибки сигналов) интерфейс отправляет в журнал приложения (rpc voice-log, строки «голос: …»); адреса
игроков туда не попадают.

Android (с 2.0.14): пока рядом есть подключённый живой собеседник или включён микрофон, оболочка держит звуковой режим
«связь» и выводит звук в динамик (если не подключены наушники или гарнитура), потому что WebView сам переключает режим при
включении и выключении микрофона, а вместе с ним меняется громкостный канал: собеседник звучал то тише, то громче.
Если WebView сбросил режим, оболочка возвращает его (проверка раз в 2 с). Выключается через 30 с после ухода последнего
собеседника или сразу при выходе из-за стола. Состояние звука (режим, маршрут, громкости каналов «связь» и «музыка», число
возвратов режима) пишется в журнал строками «звук Android (…)» при включении и выключении микрофона и смене состояния связи.

Оборванное соединение восстанавливается автоматически через сервис комнат (новое приглашение).
Неподтверждённые/устаревшие действия не применяются; партия ждёт участников.
Ручная пауза синхронна для всех и останавливает время партии. Снять её может
установивший игрок. Выход участника не завершает стол ведущего.

Офлайн-режим использует локальную комнату и тот же игровой движок; сервер
и интернет для игры с ботами не требуются.

## Сохранения и данные
Локальные настройки не входят в состояние стола. Договорённости стола сохраняются
с партией и синхронизируются ведущим. Незавершённые сохранения для продолжения
показываются ведущему; история и каталог итогов доступны участникам.
Имена для итогов комнаты объединяются, идентификаторы устройств для соединения —
нет. Сервер хранит метаданные партий, а не полные расклады.

Подробности: [SERVER](SERVER.md), [BUILD](BUILD.md), [BOTS](BOTS.md).

## Устойчивость связи (версия 2.0.5)

- Пауза приложения. Цикл heartbeat замеряет опоздание собственного тика по настенным часам. Если оно больше
  `2·интервал + 1 с`, в журнал пишется «приложение было приостановлено на N с», а молчание партнёров за время паузы
  прощается (`noteStall`). Допустимое молчание `connectionSilenceTimeoutMs` — 25 с (в 2.0.13; было 10 с, в 2.0.5 — 6 с): в партии 19.11 у ведущего-телефона были паузы сети 3–14 с, а каждый обрыв канала после 10 с молчания вёл к переподключению.
- Android: пока идёт партия или в комнате (на экране создания стола) собрались двое и больше (`PreferansAndroid.setKeepAlive`),
  работает служба переднего плана `KeepAliveService` (тип dataSync, плюс microphone, если выдано разрешение на запись звука;
  Wi-Fi lock низкой задержки, частичный wake lock до 6 ч); однократно запрашиваются разрешение на уведомления и исключение
  из экономии батареи. Пока служба работает, свёрнутое приложение продолжает разговор: `MainActivity.onPause` не усыпляет
  WebView, а JavaScript получает `preferans-voice-background` (микрофон остаётся включённым). Микрофон выключается только при
  блокировке устройства (`preferans-voice-lock`); по настройке «Восстанавливать микрофон после разблокировки» (вкладка
  «Игра», `preferans-voice-restore`, по умолчанию включена) он возвращается в состояние, бывшее перед блокировкой, по
  `preferans-voice-resume`: выключенный до блокировки микрофон остаётся выключенным.
- Локальная сеть вместо hairpin: если единственное прямое соединение с партнёром идёт через публичный адрес общего
  роутера, а в приглашении есть адреса его локальной сети, `Dial` пробует локальную сеть (`preferLAN`), а при неудаче
  возвращает прежнее соединение; повторы ограничены паузой `lanDelay`.
